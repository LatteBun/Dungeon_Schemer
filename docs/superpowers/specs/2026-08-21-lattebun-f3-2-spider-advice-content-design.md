# F3-2 거미굴 조언 콘텐츠 설계

## 문서 목적

이 문서는 F3-2 거미굴 조언 콘텐츠의 최종 설계 원본이다. 구현 단계에서는 여기 적힌 20개 사건을 다시 창작하지 않고, 이 문서의 ID·상황·조언·결과·연계 정보를 그대로 `spider-events.ts` 데이터로 옮긴다.

이번 F3-2는 단순히 사건 16개를 추가하는 작업에서, 실제 게임 플레이에 사용할 수 있는 대표 콘텐츠와 보스별 정보 구조를 함께 검증하는 수직 슬라이스로 확장한다. 따라서 사건 수는 **20개**로 잡는다.

- 일반 거미 사건 12개: `monster`
- 보스 정보 사건 8개: `special`
- 총 20개
- F3-5에서 최종 30개로 확장할 때 10개를 추가한다.

플레이어가 보는 문구는 쉬운 말을 사용한다. 내부 코드에서 `RuleId`, `BossRuleId`, `AdviceSource` 같은 이름을 사용해도 게임 화면에는 노출하지 않는다.

# 1. 설계 원칙

## 1.1 한 사건의 기본 구조

모든 사건은 다음 순서를 따른다.

1. 상황에서 **눈으로 확인할 수 있는 사실**을 보여준다.
2. 고블린이 조언 3개를 제시한다.
3. 조언은 내부적으로 도움·방해·중립 하나씩이지만 플레이어에게 유형을 보여주지 않는다.
4. 한 명이라도 조언을 수용하면 실행된다.
5. 아무도 수용하지 않으면 사건별 기본 결과로 넘어간다.

상황 문구는 결론을 직접 말하지 않는다.

- 좋은 예: `전사가 자갈을 걷어차자 거미들이 그쪽으로 몸을 돌린다.`
- 나쁜 예: `동굴거미는 진동에 민감하다.`

플레이어는 장면을 보고 결론을 내린다.

## 1.2 일반 거미 사건

일반 사건의 도움·방해는 거미굴의 생태 규칙을 근거로 한다.

- 도움: 활성 거미 습성과 맞는 조언
- 방해: 활성 거미 습성과 반대되는 조언
- 중립: 해당 습성과 무관한 조언

거미굴의 6개 규칙은 각각 도움 2개·방해 2개 이상을 공급해야 한다.

## 1.3 보스 정보 사건

보스 정보 사건은 생태 규칙이 아니라 **특정 보스의 특징**을 근거로 한다.

- 사건은 `targetBossId`를 가진다.
- 도움·방해 조언은 그 보스의 `BossRuleId`만 참조한다.
- 중립은 근거를 참조하지 않는다.
- 8개 보스 사건은 모두 지연형이다.
- 보스전 효과 공식은 공통 규칙을 사용한다.
  - 도움 수용: 보스 피해 -20%
  - 중립 수용: 보스 피해 -10%
  - 방해 수용: 보스 피해 +25%

보스마다 퍼즐은 다르지만 전투 엔진은 갈라지지 않는다.

# 2. 데이터 구조 변경

## 2.1 새 ID

`lib/domain/ids.ts`

```ts
export type BossRuleId = Brand<string, "BossRuleId">;
```

## 2.2 조언 근거

기존 `AdviceOption.ruleId?: RuleId`를 그대로 확장하지 않고, 근거를 구분된 구조로 묶는다.

```ts
export type AdviceSource =
  | { kind: "ecology"; ruleId: RuleId }
  | { kind: "boss"; bossRuleId: BossRuleId };
```

`AdviceOption`은 개념적으로 아래처럼 바뀐다.

```ts
export interface AdviceOption {
  id: ChoiceId;
  label: string;
  line: string;
  outcome: AdviceOutcome;
  source?: AdviceSource;
  relation: EcologyRelation;
  effectTags: readonly EventEffectTag[];
  bossDamageModifier?: number;
  resultText: string;
}
```

규칙:

- 도움/방해는 반드시 `source`가 있다.
- 중립은 `source`가 없다.
- `source.kind === "ecology"`면 기존 생태 규칙 검사 대상이다.
- `source.kind === "boss"`면 해당 보스 전용 특징 검사 대상이다.

## 2.3 보스 특징

`BossDef`가 보스의 이름·설명·체력·피해를 이미 소유하므로 보스 특징도 같이 둔다.

```ts
export interface BossRule {
  id: BossRuleId;
  text: string;
}

export interface BossDef {
  // 기존 필드
  rules: readonly BossRule[];
}
```

거미굴 보스는 각 2개씩 총 8개의 보스 특징을 가진다.

`rules`는 모든 `BossDef`의 필수 필드다. F3-2에서는 거미굴 보스만 각 2개를
채우고, 사막·묘지 보스는 F3-3에서 전용 정보를 작성할 때까지 빈 배열을 둔다.
이렇게 하면 보스 특징을 한 모델로 유지하면서도 아직 작성하지 않은 테마의
특징을 임의로 창작하지 않는다. 테마 검증기는 `rules` 배열 자체와 배열 안의
ID·문구 중복·빈 값을 검사하되, F3-2 시점에 빈 배열인 것을 오류로 보지 않는다.

## 2.4 보스 대상 사건

`SituationEvent`에 다음 필드를 추가한다.

```ts
targetBossId?: BossId;
```

규칙:

- 일반 거미 사건: `targetBossId` 없음
- 보스 정보 사건: `targetBossId` 필수
- 보스 정보 사건은 이번 F3-2에서 모두 `kind: "special"`
- `targetBossId`가 없으면 어떤 조언도 `source.kind: "boss"` 또는
  `bossDamageModifier`를 가질 수 없다.
- `targetBossId`가 있으면 세 조언 모두 `bossDamageModifier`를 가지며,
  도움·방해의 source는 `kind: "boss"`여야 한다.

# 3. 거미굴 보스 특징 8개

## 3.1 거대거미 라그나 — `boss-spider-1`

### `boss-ragna-turning`

**큰 몸 때문에 급하게 방향을 바꾸기 어렵다.**

플레이어에게는 이 문장을 직접 보여주지 않는다. 좁은 곳에서 몸을 돌리다가 벽에 부딪히는 장면으로 보여준다.

### `boss-ragna-crouch`

**큰 공격을 하기 직전에 몸을 낮춘다.**

플레이어에게는 달려들기 전에 자세를 낮추고 잠깐 멈추는 장면으로 보여준다.

## 3.2 고치관리자 모르칸 — `boss-spider-2`

### `boss-morkan-cocoon-side`

**모르칸이 만든 고치는 한쪽 면이 더 얇다.**

빈 고치가 항상 같은 쪽으로 찢어진 모습을 보여준다.

### `boss-morkan-spin-pause`

**새 거미줄을 만들 때 잠깐 움직임이 둔해진다.**

거미줄을 뽑는 동안 다리 움직임이 느려지는 장면으로 보여준다.

## 3.3 아라크네 세리나 — `boss-spider-3`

### `boss-serina-web-hub`

**여러 거미줄을 한꺼번에 당긴다.**

한 줄을 건드렸는데 멀리 떨어진 여러 줄까지 같이 팽팽해지는 장면으로 보여준다.

### `boss-serina-block-retreat`

**공격하기 전에 상대의 퇴로부터 막는다.**

작은 짐승을 바로 덮치지 않고 뒤쪽 길부터 거미줄로 막는 장면으로 보여준다.

## 3.4 거미여왕 아라크샤 — `boss-spider-4`

### `boss-araksha-swarm-follow`

**주변 새끼거미가 여왕의 움직임을 따라 움직인다.**

여왕이 방향을 바꾸자 주변 새끼들이 같은 방향으로 움직이는 장면으로 보여준다.

### `boss-araksha-summon-first`

**여왕이 위협받으면 직접 달려들기 전에 주변 거미를 먼저 불러들인다.**

여왕이 몸을 일으키자 주변 구멍에서 거미들이 먼저 몰려나오는 장면으로 보여준다.

# 4. 일반 거미 사건 12개

아래 12개가 F3-2의 일반 콘텐츠 원본이다.

## SP01 — 떨어진 횃불

- ID: `spider-fire-floor-torch`
- kind: `monster`
- theme: `spider`
- 난이도 역할: 기본 학습
- 도움 근거: `spider-fire`
- 방해 근거: `spider-fire`

**상황**

동굴거미들이 좁은 길을 막고 있다. 바닥에 떨어진 횃불 가까이에 있던 거미 한 마리가 불빛을 피해 슬금슬금 뒤로 물러난다.

**조언 1 — 도움**

- 선택지: `횃불을 앞쪽 바닥에 던져 길을 벌리세요.`
- 고블린 대사: `불 가까이는 싫어하는 것 같아요. 앞으로 던져보죠.`
- source: `ecology / spider-fire`
- relation: `consistent`
- 결과: `횃불이 바닥을 구르자 거미들이 양옆으로 물러나고 파티가 그 틈으로 빠져나간다.`

**조언 2 — 방해**

- 선택지: `불을 뒤로 치우고 그대로 밀고 나가세요.`
- 고블린 대사: `불빛 때문에 더 흥분할 수도 있어요. 치우는 게 나아요.`
- source: `ecology / spider-fire`
- relation: `contradictory`
- 결과: `불이 멀어지자 거미들이 다시 통로 한가운데로 몰려들어 파티의 움직임을 막는다.`

**조언 3 — 중립**

- 선택지: `방패를 붙이고 천천히 전진하세요.`
- 고블린 대사: `급하게 움직이지 말고 방패부터 붙여요.`
- source: 없음
- relation: `unrelated`
- 결과: `파티가 방패를 맞대고 조금씩 전진해 큰 손해 없이 길을 지난다.`

**아무도 믿지 않았을 때**

파티가 짧게 거미들을 밀어내고 지나가지만 시간을 조금 더 쓴다.

**기본 결과**

파티가 거미줄 일부를 잘라내며 천천히 통로를 지난다.

# 7. 검증 규칙

## 7.1 기존 기본 검증 유지

- 사건마다 조언 정확히 3개
- 도움·방해·중립 정확히 하나씩
- 사건 ID 전역 중복 금지
- 사건 제목·상황·기본 결과 비어 있으면 오류
- 조언 선택지·고블린 대사·결과 문구 비어 있으면 오류
- 약한 연계 강화판은 기존 슬롯과 같은 outcome 유지
- 공용 사건은 생태/보스 source를 가질 수 없음

## 7.2 테마 전체를 기준으로 검증

기존 `validateSituationEvents(events)` 호출은 공용 콘텐츠를 위해 유지한다.
이 호출은 현재처럼 공용 사건의 분류별 공급량을 검사한다.

테마 콘텐츠를 검증할 때는 개념적으로 다음 호출을 허용한다.

```ts
validateSituationEvents(SPIDER_EVENTS, SPIDER_THEME)
```

두 번째 인자를 받은 호출은 **테마 전용 검증 모드**다. 이 모드에서는 공용
사건 공급량을 검사하지 않고, 모든 사건의 `theme`이 전달받은 `ThemeContent.id`와
같은지 확인한다. 반대로 인자 하나인 기존 호출은 공용 콘텐츠와 기존의 혼합
검증 호환성을 유지한다.

`ThemeContent`를 받았을 때는 실제 콘텐츠에 등장한 ruleId만 검사하지 않고, **테마가 가진 6개 규칙 전체를 기준으로 공급량을 검사한다.**

따라서 어느 규칙이 0회 참조되어도 누락을 잡는다.

또한 다른 테마의 RuleId를 참조하면 오류다.

## 7.3 보스 특징 검증

보스 정보 사건은 다음을 확인한다.

- `targetBossId` 필수
- `kind === "special"`
- 도움/방해 source는 `kind: "boss"`
- 참조 `BossRuleId`가 `targetBossId` 보스의 rules 안에 실제로 존재
- 다른 보스 특징을 참조하면 오류
- 중립은 source 없음
- 세 조언 모두 `bossDamageModifier`를 가짐

보스 대상이 없는 사건은 boss source와 `bossDamageModifier`를 가지면 오류다.
보스 대상 사건이 생태 source를 가지거나, 대상 보스가 전달받은 테마에 없거나,
사건의 `theme`과 대상 보스의 theme이 다르면 오류다.

수치 자체의 산술 적용과 합산 상한은 E2/E4의 책임이다. F3-2는 정보 사건인데 보정값을 빠뜨리는 구조 오류까지만 막는다.

## 7.4 거미굴 전용 테스트

`spider-events.test.ts`에서 다음을 명시적으로 확인한다.

- 총 20개
- monster 12개
- special 8개
- 모든 사건 theme = `spider`
- 보스별 정보 사건 2개씩
- 6개 생태 규칙 각각 도움 2개 이상·방해 2개 이상
- 약한 연계 1세트 이상
- 강한 연계 2세트 이상
- 전체 20개가 범용 검증기를 통과

20이라는 숫자는 범용 검증기에 넣지 않는다. F3-5에서 30개로 늘어나도 범용 검증기가 깨지지 않아야 한다.

# 9. 작업표 수정

현재 F3-2 작업 배정표의 `거미굴 전용 사건 16개`는 구현 시 **20개**로 수정해야 한다.

완료 기준은 다음 의미로 바뀐다.

- 거미굴 전용 사건 20개
- 일반 monster 12개 + 보스 special 8개
- 생태 규칙마다 도움 2개·방해 2개 이상
- 보스 4종마다 전용 정보 2개
- 중립은 각 사건 1개로 충분히 공급
- 약한 연계 1세트 이상
- 강한 연계 2세트 이상
- 테마 전체 규칙 누락과 잘못된 규칙 참조를 검증기가 차단
- 보스 정보가 다른 보스의 특징을 참조하면 검증 실패

# 10. 범위 밖

이번 F3-2에서 하지 않는다.

- 보스마다 별도 전투 상태이상/소환/고치 시스템 구현
- 보스별 전투 AI 분기
- 사막·묘지 조언 콘텐츠 작성
- F3-5 최종 30개 확장분 10개 작성
- E2의 실제 수용·의심·적발 계산 구현
- E3의 최종 사건 배치 알고리즘 구현
- E4의 보스전 피해 적용 구현

F3-2는 **콘텐츠 20개 + 이를 안전하게 표현하고 검증할 계약**까지를 범위로 한다.
