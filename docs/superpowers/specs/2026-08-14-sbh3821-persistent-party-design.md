# C2 지속 파티 설계

**작성자:** sbh3821
**작성 도구:** Claude Code

## 목적

탐험 정산 뒤에도 인물이 캠페인 내내 이어지게 한다. 3명 생존 팀은 유지하고,
1~2명 생존 팀은 예비 인원으로 충원하며, 그것으로 안 되면 손상 파티의
생존자를 자동 재편한다. 출전하지 않은 생존자는 조금씩 회복한다.

이 작업은 [프로토타입 작업 배정표](../../technical/PROTOTYPE_WORK_ASSIGNMENT.md)의
`C2`이고 상세 plan의 **Task 4**에 대응한다. 완료되면 `C3` 정산·승급·엔딩의
선행 하나가 풀린다.

상위 기준은 [게임 방향 개편 설계](2026-08-13-sanghwan-yoo-game-direction-rework-design.md)와
[파티와 신뢰](../../systems/PARTY_AND_TRUST.md)이며, 이 문서는 그 규칙을
구현 계약으로 옮긴 것이다. 두 문서와 충돌하면 상위 문서를 따른다.

## 설계 원칙

### 상태는 인물에 귀속한다

HP·신뢰·소지 골드·행동 기억은 파티가 아니라 `MemberId`에 붙는다. 재편으로
파티가 바뀌어도 이 값들은 따라다닌다. 파티는 "지금 누구와 함께 나가는가"만
표현하는 껍데기다. 이것이 흔들리면 신뢰를 쌓았다 배신하는 서사가 판마다
초기화된다.

### 순수 함수만 제공한다

`CampaignState`와 정산 결과를 받아 새 `CampaignState`를 반환한다. 입력을
변경하지 않고 스토어·화면·부수효과를 포함하지 않는다. 난수는 만들지 않고
`regroup` 스트림에서 파생한 `Rng`를 인자로 받는다.

### 조용히 보정하지 않는다

존재하지 않는 인물 ID, 이미 죽은 인물의 생존 보고, 중복 ID는 기본값으로
덮지 않고 `RuleError`를 던진다. 재편이 실패해도 무작위로 다시 뽑지 않는다.
파티를 하나도 만들 수 없는 상태는 오류가 아니라 `partyExhausted` 엔딩의
입력이므로 그대로 반환한다.

## 공개 계약

```ts
/** 정산 결과를 받아 파티 유지·충원·재편·회복을 한 번에 적용한다. */
export function maintainPartiesAfterExpedition(
  state: CampaignState,
  result: ExpeditionResult,
  rng: Rng,
): CampaignState;

/** 주어진 인물들로 만들 수 있는 최대 수의 완성 3인 파티를 만든다. */
export function regroupSurvivors(
  memberIds: readonly MemberId[],
  availableMembers: readonly CampaignMember[],
  rng: Rng,
): CampaignParty[];

/** 출전하지 않은 생존자만 회복시킨 새 인물 목록을 반환한다. */
export function healNonParticipants(
  members: readonly CampaignMember[],
  participantIds: ReadonlySet<MemberId>,
): CampaignMember[];
```

호출 예는 `maintainPartiesAfterExpedition(state, result, createRng(state.seed).derive("regroup"))`이다.

## 처리 순서

`maintainPartiesAfterExpedition`은 다음 순서를 지킨다. 순서가 바뀌면
회복 대상과 충원 결과가 달라진다.

1. 입력을 검증한다.
2. 사망자를 `alive: false`로 바꾸고 출전 파티에서 뺀다.
3. 3명 생존 파티는 그대로 둔다.
4. 1~2명 생존 파티를 직업이 겹치지 않는 예비 인원으로 충원한다.
5. 충원으로 완성하지 못하면 손상 파티 생존자·대기 인물·남은 예비를 모아
   자동 재편한다.
6. 완성 파티에 못 들어간 생존자를 대기 명단에 넣는다.
7. 이번 탐험에 출전하지 않은 생존자를 회복시킨다.

출전자 명단은 반드시 `result`의 생존·사망 목록에서 읽는다. 재편 뒤의 파티
구성에서 읽으면 충원으로 들어온 예비가 출전자로 오인되고, 다른 파티로
옮겨간 생존자가 비출전자로 오인된다.

회복(7)은 3~6단계와 교환 가능하다. 충원·재편이 `currentHp`를 읽지 않기
때문이다. 그래도 순서를 고정하는 이유는 나중에 재편이 HP를 참고하게 될 때
결과가 갈리지 않게 하려는 것이다.

## 충원

1~2명이 생존한 파티는 부족한 인원을 예비 인원에서 채운다.

- 파티에 이미 있는 직업과 겹치지 않는 예비만 후보다.
- 후보가 여럿이면 `regroup` 스트림으로 고른다.
- 예비 인원이 모자라 완성하지 못하면 그 파티는 손상 상태로 남아 재편 대상이
  된다.
- 충원에 쓰인 인물은 `reserveMemberIds`에서 뺀다.

손상 파티가 여럿이면 **생존자가 많은 파티부터** 충원한다. 2명 팀은 한 명만
채우면 완성되므로, 1명 팀을 먼저 채워 예비를 소진하는 것보다 완성 파티 수가
많아진다.

## 자동 재편

충원 뒤에도 손상 파티가 남으면 손상 파티의 생존자, 대기 인물, 남은 예비를
한 풀로 모아 다시 3인 파티를 짠다.

### 우선순위

1. 완성 가능한 3인 파티 수 최대화
2. 기존 동료가 함께 남는 쌍의 수 최대화
3. 동률이면 캠페인 시드로 결정

### 최대 파티 수는 정확히 계산한다

한 파티는 서로 다른 직업 3명이므로 한 직업은 파티마다 최대 한 명 들어간다.
직업별 인원을 `c_i`라 할 때 파티 `k`개를 만들 수 있는 조건은 다음과 같다.

```text
sum_i min(c_i, k) >= 3k
```

`k`를 `floor(전체 인원 / 3)`부터 0까지 내리며 이 조건을 만족하는 첫 값이
최대 파티 수다. 탐색이 아니라 계산이므로 결과가 항상 최적이다.

### 동료 쌍 최대화는 탐욕적으로 한다

`k`를 정한 뒤에는 파티를 하나씩 채운다. 각 자리에서 남은 인원이 가장 많은
직업들을 먼저 쓰고, 같은 직업 후보 중에서는 **이미 그 파티에 앉은 사람과
전에 같은 파티였던 사람**을 우선한다. 동률이면 `regroup` 스트림으로 고른다.

쌍 최대화의 전역 최적해는 조합 폭발이라 프로토타입 범위에서 풀지 않는다.
파티 수(1순위)는 위 계산으로 항상 최적이고, 쌍(2순위)만 탐욕적이다. 이
근사는 의도된 것이며, 백테스트에서 재편 품질이 문제로 드러나면 그때
개선한다.

"전에 같은 파티였다"는 판단은 이번 재편 **직전**의 파티 구성을 기준으로 한다.
재편 도중 만들어진 새 파티는 동료로 세지 않는다.

## 비출전 회복

```text
회복량 = max(1, round(현재 HP × 0.05))
회복 후 HP = min(최대 HP, 현재 HP + 회복량)
```

- 이번 탐험 출전자는 제외한다. 생존자든 사망자든 마찬가지다.
- 죽은 인물은 회복하지 않는다.
- 게시판 등장 여부, 완성 파티 소속 여부와 무관하다. 대기 인물과 예비 인원도
  회복한다.
- 이미 최대 HP인 인물은 그대로 둔다.

`round`는 JavaScript 기본 동작을 쓴다. 현재 HP 19면 `round(0.95) = 1`이라
20이 되고, 1이면 `round(0.05) = 0`이지만 최소 1이 적용되어 2가 된다.

## 변화 기록

파티 구성이 바뀐 이유는 바뀌는 순간에만 존재한다. 정산이 나중에 이전·이후
상태를 비교하면 **무엇이** 바뀌었는지는 알 수 있지만 **왜** 바뀌었는지는
알 수 없다. 같은 결과가 충원으로도 재편으로도 나올 수 있기 때문이다.
그래서 `maintainPartiesAfterExpedition`이 `CampaignState.log`에 기록을
남긴다.

상위 spec이 "정산은 선택→개인 반응→피해·신뢰→보상·손실→승급·파티 변화의
원인 사슬을 보여준다"고 요구하는데, 이 기록이 그 사슬의 마지막 칸을
채운다.

| 상황 | 요약 형식 |
| --- | --- |
| 충원 | `<파티 ID> 충원 · <합류자 이름 목록>` |
| 재편 | `재편 · 손상 <해체한 팀 수>팀에서 완성 <만든 팀 수>팀` |
| 대기 | `대기 · <대기자 이름 목록>` |

- 기록은 추가 전용이다. 기존 `log`를 고치지 않는다.
- `at`은 기존 `log.length`부터 1씩 올린다. 시각이 아니라 순번이다.
  시각을 쓰면 재현성이 깨진다.
- 변화가 없으면 아무것도 남기지 않는다. 3명 전원 생존은 로그를 늘리지
  않는다.
- 사망 자체는 기록하지 않는다. 사망 사유는 `result`가 갖고 있고 정산이
  기록한다. 여기서는 사망이 만든 **파티 구성 변화**만 남긴다.
- 회복은 기록하지 않는다. 매 정산마다 비출전자 수만큼 줄이 늘어 원인
  사슬을 덮는다. 회복량은 인물의 HP 변화로 이미 드러난다.

요약 문구는 잠정 형식이다. 화면 작업이 다듬을 수 있으나 순번 규칙과
"충원·재편·대기 셋만 남긴다"는 범위는 유지한다.

## 오류 처리

다음은 `RuleError`다. 조용히 보정하지 않는다.

| 조건 | 코드 |
| --- | --- |
| `result`의 인물 ID가 캠페인에 없음 | `UNKNOWN_ID` |
| 생존자와 사망자 목록에 같은 ID가 있음 | `DUPLICATE_ID` |
| 이미 죽은 인물이 생존자로 보고됨 | `INVALID_SETTLEMENT` |
| 출전 인물이 어떤 파티에도 속하지 않음 | `INVALID_SETTLEMENT` |

검증은 상태를 만들기 전에 실행한다. 거부된 호출은 어떤 상태도 바꾸지 않는다.

## 테스트

### 유지와 충원

- 3명 생존 파티는 구성이 그대로다.
- 2명 생존 파티가 직업이 겹치지 않는 예비 한 명으로 완성된다.
- 1명 생존 파티가 예비 두 명으로 완성된다.
- 충원한 파티 안에 직업 중복이 없다.
- 충원에 쓰인 예비는 `reserveMemberIds`에서 빠진다.
- 예비가 부족하면 그 파티는 완성되지 않고 남는다.
- 생존자가 많은 파티부터 충원해 완성 파티 수가 더 많아진다.

### 재편

- 예비로 완성할 수 없을 때 손상 파티 생존자들이 새 파티로 묶인다.
- 만들어진 완성 파티 수가 `sum_i min(c_i, k) >= 3k` 최대값과 같다.
- 모든 완성 파티의 직업이 서로 다르다.
- 같은 입력과 같은 시드는 같은 재편 결과를 만든다.
- 완성 파티에 못 들어간 생존자가 대기 명단에 남는다.
- 완성 파티를 하나도 만들 수 없으면 오류 없이 빈 결과를 반환한다.

### 개인 상태 보존

- 재편 전후로 인물의 HP·신뢰·소지 골드·기억·직업·성격이 같다.
- 사망자는 `alive: false`가 되고 어떤 파티에도 남지 않는다.

### 회복

- `healNonParticipants([HP 19, HP 1], 빈 집합)`이 `[20, 2]`를 만든다.
- 출전자는 회복하지 않는다.
- 회복이 최대 HP를 넘지 않는다.
- 죽은 인물은 회복하지 않는다.
- 대기 인물과 예비 인원도 회복한다.

### 변화 기록

- 충원이 일어나면 파티 ID와 합류자가 담긴 기록이 남는다.
- 재편이 일어나면 해체한 팀 수와 만든 팀 수가 담긴 기록이 남는다.
- 대기자가 생기면 이름이 담긴 기록이 남는다.
- 3명 전원 생존처럼 변화가 없으면 로그가 늘지 않는다.
- `at`이 기존 `log.length`부터 1씩 이어진다.
- 기존 로그 항목이 그대로 보존된다.

### 오류와 불변성

- 위 오류 표의 네 조건이 각각 `RuleError`를 던진다.
- 거부된 호출 전후로 입력 상태가 같다.
- 성공한 호출도 입력 `state`와 `result`를 변경하지 않는다.

전체 완료 검증은 `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` 넷이다.

## 제외 범위

- 계약 보상, 명성·골드 정산, 던전 등급 상승, 승급 (`C3`)
- 엔딩 판정. `partyExhausted`의 입력만 만들고 판정은 하지 않는다 (`C3`)
- 탐험 진행과 생존·사망 결정 (`E3`)
- 새 인물 생성. 예비 인원 보충은 이번 프로토타입에 없다
- 화면 표시 (`U1`·`U3`)
- 신뢰 변화. 재편은 신뢰를 건드리지 않는다

## 후속 작업 계약

- `C3`는 이 함수를 정산 순서의 5~6단계에서 호출하고, 반환된 상태로 엔딩을
  판정한다.
- `C1`의 `generateBoard`는 재편 결과의 완성 파티만 공고에 연결한다.
- `U1`은 대기 인물과 손상 파티를 화면에 드러낸다.
- `C4` 백테스트는 재편 품질(완성 파티 수, 대기 인원)을 보고 항목으로 쓴다.
