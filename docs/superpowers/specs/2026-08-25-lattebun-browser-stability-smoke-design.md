# 브라우저 안정성 스모크 테스트 설계

- 작성일: 2026-08-25
- 작성자: lattebun
- 작성 도구: Codex
- 대상 작업: 로컬 브라우저 안정성 회귀 테스트
- 기준 브랜치: `main`
- 기준 커밋: `1499979` (PR #155 병합)

## 1. 문서의 지위

이 문서는 최신 `main`의 공개 화면과 핵심 캠페인 클릭 흐름을 실제 Chromium에서
반복 검증하는 로컬 E2E 테스트의 계약을 정의한다. 기존 Vitest 회귀는 규칙과 Store
상태 전이를 검증하지만, Next.js 라우트 렌더링·브라우저 런타임 예외·사용자 클릭에
따른 화면 전이는 직접 검증하지 않는다. 이 간극을 Playwright 스모크 테스트로
보완한다.

이 테스트는 밸런스 수치를 판정하거나 시각적 완성도를 새로 정의하지 않는다.
`docs/experience/SCREEN_LAYOUT.md`와
`docs/experience/UI_IMPLEMENTATION_GUIDE.md`에 이미 정해진 고정 캔버스 계약을
자동으로 확인하는 안전망이다.

## 2. 목표와 비목표

### 2.1 목표

- `pnpm test:e2e` 한 명령으로 Next.js 서버 기동부터 Chromium 테스트 종료까지
  수행한다.
- 공개 검증 경로가 HTTP 오류, 빈 화면, Next.js 오류 오버레이, 브라우저
  `pageerror` 없이 렌더링되는지 확인한다.
- 캠페인의 시작부터 첫 사건 결과까지 핵심 사용자 흐름을 실제 접근성 역할과
  표시 이름으로 조작한다.
- 공식 네 viewport에서 1920×1080 고정 캔버스의 비율, 중앙 정렬, 레터박스,
  무스크롤 계약을 검증한다.
- 실패 시 어느 경로·단계·viewport에서 깨졌는지 Playwright 리포트와 실패
  산출물로 재현할 수 있게 한다.
- 테스트 설치와 실행 방법을 공식 개발 환경 문서에 기록한다.

### 2.2 비목표

- GitHub Actions나 Vercel에 E2E 테스트를 연결하지 않는다.
- Firefox·WebKit·모바일 전용 재배치 UI를 검증하지 않는다.
- 모든 조언 조합이나 캠페인 15회 완주를 브라우저에서 반복하지 않는다. 전체
  캠페인 규칙 회귀는 기존 Vitest가 소유한다.
- 픽셀 단위 골든 스크린샷 비교를 도입하지 않는다.
- 성능 예산, WCAG 전체 감사, 네트워크 장애 주입을 이번 범위에 포함하지 않는다.
- `agent-browser` 전역 설치를 프로젝트 실행 전제로 삼지 않는다.

## 3. 도구 선택

`@playwright/test`를 `devDependency`로 고정하고 Chromium 한 종류만 사용한다.
Next.js 16의 저장소 내 공식 가이드는 Playwright를 E2E 도구로 안내하며,
`webServer`로 Next.js 서버를 자동 기동할 수 있다고 명시한다.

전역 `agent-browser` 셸 스크립트는 사람과 AI가 탐색적으로 화면을 확인할 때는
유용하지만, 버전 고정·assertion·리포트·실패 위치 추적이 저장소 테스트 러너보다
약하므로 정식 회귀 테스트 기반으로 사용하지 않는다. 다중 브라우저 검증은 현재
공식 UI 검증 기준이 실제 Chromium인 점과 실행 비용을 고려해 후속 범위로 둔다.

## 4. 실행 구조

### 4.1 패키지와 명령

- `@playwright/test`를 개발 의존성에 추가하고 `pnpm-lock.yaml`에 고정한다.
- `pnpm test:e2e:install`은 Playwright가 관리하는 Chromium을 설치한다.
- `pnpm test:e2e`은 로컬 Chromium E2E 전체를 한 번 실행하고 종료한다.
- `playwright.config.ts`는 고정된 별도 포트에서 Next.js 개발 서버를 기동하고
  `baseURL`을 제공한다.
- 로컬 편의를 위해 이미 같은 URL의 서버가 있으면 재사용할 수 있지만, CI 연결을
  추가할 때는 새 서버 사용을 기본으로 다시 검토한다.

브라우저 바이너리는 저장소에 커밋하지 않는다. Playwright의 `test-results/`와
`playwright-report/`도 `.gitignore`에 추가한다.

### 4.2 테스트 파일 경계

브라우저 E2E는 `e2e/` 아래에 둔다. 기존 "대상 옆 `<대상>.test.ts`" 규칙은 Node
환경의 Vitest 단위·통합 테스트에 계속 적용한다. 브라우저 프로세스와 실제 서버가
필요한 Playwright spec은 이름 충돌과 러너 중복 수집을 피하기 위해
`e2e/*.spec.ts`로 분리한다.

책임은 다음 세 묶음으로 나눈다.

1. **공개 경로 스모크**: 각 경로의 응답, 본문, 대표 landmark 또는 제목, 오류
   오버레이, 브라우저 예외를 검증한다.
2. **캠페인 핵심 흐름**: 인트로부터 첫 사건 결과까지 실제 클릭 전이를 검증한다.
3. **고정 캔버스 계약**: 공식 viewport별 캔버스 크기·위치·스크롤을 검증한다.

공통 브라우저 오류 수집과 캔버스 측정은 작은 helper로 분리하되, 테스트 의미를
숨기는 범용 프레임워크는 만들지 않는다.

## 5. 공개 경로 스모크 계약

검사 경로는 현재 빌드가 공개하는 다음 아홉 개다.

- `/`
- `/campaign`
- `/u1-test`
- `/u2-test`
- `/u3-test`
- `/u4-test`
- `/u5-test`
- `/u5-2-test`
- `/u6-test`

각 경로는 다음을 만족해야 한다.

- 최상위 document 응답이 성공 상태다.
- `body.innerText.trim()`이 비어 있지 않다.
- 해당 화면의 안정된 landmark, 제목 또는 고유 표시 문구가 보인다. 정확한 수치나
  시드에 따라 바뀌는 콘텐츠 전문은 고정하지 않는다.
- `[data-nextjs-dialog]` 오류 오버레이가 없다.
- 탐색 중 수집한 `pageerror`가 없다.
- `console.error`는 테스트 실패로 취급한다. 단, 프레임워크가 의도적으로 출력하는
  것으로 확인된 메시지가 생기면 문자열 전체를 광범위하게 무시하지 않고 출처와
  이유가 드러나는 좁은 예외를 둔다.

라우트 목록은 한 곳에서 관리해 새 공개 검증 화면이 추가될 때 누락을 발견하기
쉽게 한다. 다만 파일 시스템을 읽어 모든 라우트를 자동 추론하지는 않는다. 동적
라우트와 내부 라우트의 의도까지 테스트가 추측하지 않도록 명시적 목록을 유지한다.

## 6. 캠페인 핵심 흐름 계약

브라우저 컨텍스트를 새로 시작한 뒤 다음 순서를 검증한다.

```text
/campaign
→ 길드 게시판으로
→ 진입 가능한 첫 공고 선택
→ 이 공고 계약하기
→ 선택 가능한 전투 지점 선택
→ 이 지점으로 이동
→ 표시된 조언 하나 선택
→ 사건 결과·수치/신뢰 변화 표시
→ 지도로 돌아가는 동작 활성화
```

선택자는 DOM 구조나 자동 생성 class가 아니라 `role`, 접근 가능한 이름, region과
heading을 우선한다. 게시판·지도·조언의 구체 콘텐츠가 시드에 따라 달라도
"진입 가능", "지점 선택", "이 지점으로 이동"처럼 사용자에게 보이는 계약으로
첫 유효 항목을 고른다.

각 전이 뒤에는 다음 화면의 고유 region 또는 heading이 나타날 때까지 기다린다.
고정 시간 `sleep`은 쓰지 않는다. 애니메이션이 진행 중이어도 Playwright의
actionability와 화면 상태 조건으로 동기화한다. 전 과정에서 `pageerror`와
`console.error` 수집을 유지한다.

이 테스트는 조언의 도움·방해 분류나 전투 수치를 단정하지 않는다. 어느 유효
조언을 골라도 결과 화면까지 도달하는 UI 연결만 검증한다.

## 7. 고정 캔버스 계약

공식 viewport는 다음 네 가지다.

| viewport | 기대 |
| --- | --- |
| 1920×1080 | 레터박스 없이 16:9 캔버스 |
| 2560×1440 | 레터박스 없이 16:9 캔버스 |
| 1440×900 | 위아래 레터박스, 중앙 정렬 |
| 1280×1024 | 더 두꺼운 위아래 레터박스, 중앙 정렬 |

각 viewport에서 대표 캠페인 화면과 U5·U6 화면을 열어 다음 값을 브라우저의 실제
bounding box와 document 치수로 검사한다.

- document의 가로·세로 스크롤 범위가 viewport를 넘지 않는다.
- `.game-canvas`의 실제 비율이 허용 오차 안에서 16:9다.
- 캔버스의 좌우·상하 여백 차이가 반올림 오차 범위 안에서 같다.
- 일반 화면 루트가 캔버스 폭과 높이를 전부 점유한다. 공식적으로
  `data-canvas-layout="intrinsic"`가 지정된 예외는 전체 점유 assertion에서 제외한다.
- 주요 카드와 이미지가 캔버스 밖으로 넘치지 않는다.

브라우저 subpixel 반올림을 고려해 위치와 크기에는 작은 절대 오차를 허용한다.
계약을 무력화할 정도의 비율 오차나 큰 overflow는 허용하지 않는다.

390px 모바일에서 UI를 재배치하거나 글자 크기를 별도로 보장하지 않는다. 공식
규칙은 창이 작아질 때 1920×1080 그림 전체를 균일 축소하는 것이므로, 모바일
viewport도 필요하면 후속 가독성 정책을 먼저 승인한 뒤 추가한다.

## 8. 실패 진단과 산출물

- 실패 시 trace와 screenshot을 보존하고, 성공 시에는 불필요한 산출물을 남기지
  않는다.
- 실패 메시지에는 경로 또는 캠페인 단계와 viewport 이름이 드러나야 한다.
- 테스트 종료 후 Playwright가 시작한 서버와 브라우저 프로세스가 종료되어야 한다.
- 테스트가 실패해도 앱의 Zustand 상태나 브라우저 storage를 다음 테스트에
  공유하지 않는다.
- 랜덤 콘텐츠 때문에 실패했다면 출력에 현재 URL과 화면에서 선택한 접근 가능
  이름을 남겨 같은 단계의 원인을 찾을 수 있게 한다. 테스트 통과를 위해 조용히
  페이지를 새로고침하거나 새 캠페인을 재추첨하지 않는다.

## 9. 공식 문서 갱신

`docs/technical/DEVELOPMENT_ENVIRONMENT.md`에 다음을 추가한다.

- Playwright와 Chromium의 역할
- 최초 `pnpm test:e2e:install` 실행
- 일상적인 `pnpm test:e2e` 실행
- 브라우저 스모크와 Vitest가 각각 소유하는 검증 범위
- 실패 산출물 위치와 PR 전 권장 검증 순서
- E2E 파일은 `e2e/*.spec.ts`에 둔다는 Vitest 공존 예외

`docs/README.md`에는 이 설계와 구현 계획을 기술 문서 인덱스에서 찾을 수 있게
연결한다. 게임 규칙은 바뀌지 않으므로 `docs/GAME_PRINCIPLES.md`와 시스템 규칙
문서는 수정하지 않는다.

## 10. 예상 영향 파일

- `package.json`: Playwright 설치·실행 스크립트와 개발 의존성
- `pnpm-lock.yaml`: 고정된 Playwright 의존성
- `playwright.config.ts`: Chromium, baseURL, webServer, 실패 산출물 설정
- `e2e/routes.spec.ts`: 공개 경로 렌더링과 브라우저 오류 회귀
- `e2e/campaign-smoke.spec.ts`: 첫 사건 결과까지 핵심 클릭 흐름
- `e2e/canvas-layout.spec.ts`: 공식 viewport 고정 캔버스 계약
- 필요 시 `e2e/browser-errors.ts`: 좁은 범위의 공통 오류 수집 helper
- `.gitignore`: Playwright 실행 산출물 제외
- `docs/technical/DEVELOPMENT_ENVIRONMENT.md`: 설치·실행·책임 경계
- `docs/README.md`: 설계와 계획 링크

## 11. 완료 기준

- 새 checkout에서 `pnpm install --frozen-lockfile` 뒤
  `pnpm test:e2e:install`로 Chromium을 준비할 수 있다.
- `pnpm test:e2e` 하나로 서버 기동, 세 테스트 묶음, 정리가 자동 수행된다.
- 아홉 공개 경로, 첫 사건 결과까지의 캠페인 흐름, 공식 네 viewport 캔버스 계약이
  Chromium에서 검증된다.
- 테스트는 숨은 수치나 특정 랜덤 콘텐츠에 결합하지 않고 실제 사용자 관점의
  안정된 화면 계약을 사용한다.
- 기존 `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` 검증과 충돌하지
  않는다.
- CI 연동, 다중 브라우저, 골든 스크린샷은 후속 결정 전까지 범위 밖으로 남는다.
