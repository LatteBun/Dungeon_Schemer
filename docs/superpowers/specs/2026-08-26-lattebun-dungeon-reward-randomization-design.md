# 던전 계약 보상 랜덤화 설계

- 작성자: LatteBun
- 작성 도구: Codex
- 작업 분류: 게시판·정산·밸런스 변경
- 상태: 사용자 설계 승인 완료, 구현 계획 작성 완료

## 1. 목적

같은 위험도의 공고가 보상까지 같아 반복적으로 느껴지는 문제를 줄인다. 위험도별
평균 보상과 생존 인원별 지급 비율은 유지하면서, 공고마다 명성과 골드를 정해진
범위에서 독립적으로 추첨해 게시판에서 비교할 이유를 만든다.

보상은 렌더링이나 정산 시점에 다시 계산하지 않는다. 공고 생성 시 확정한 값을
계약과 원정, 정산까지 전달해 플레이어가 계약 전에 본 숫자가 결과와 일치하게 한다.

## 2. 목표와 비목표

### 목표

- 같은 위험도 공고도 명성·골드 조합이 달라질 수 있다.
- 위험도별 명성·골드 기대값은 기존 고정값과 정확히 같다.
- 같은 캠페인 시드·월드턴·던전·위험도는 같은 보상을 만든다.
- 게시판은 공고에 이미 확정된 보상만 보여준다.
- 정산은 계약 당시 확정 보상에 생존 비율 또는 전멸 손실을 적용한다.
- 잠금 공고와 백테스트 공개 상태도 생산 게시판과 같은 확정 보상을 사용한다.

### 비목표

- 생존 비율, 승급 문턱, 유품, 위험도 상승 규칙을 다시 조정하지 않는다.
- 보상 범위를 게시판이나 정산 화면에 표시하지 않는다.
- 전멸 정산에서 다음 공고의 보상을 미리 생성하거나 예고하지 않는다.
- 게시판 배치, 카드 디자인, 정산 화면의 다른 정보 구조를 재설계하지 않는다.
- 백테스트 결과를 근거로 승인 없이 범위·비율·승급 수치를 자동 조정하지 않는다.

## 3. 확정 보상 계약

`ContractReward`는 공고에 기록하는 **3명 생존 기준** 명성·골드다.

```ts
export interface ContractReward {
  readonly reputation: number;
  readonly gold: number;
}

export interface BoardOffer {
  readonly id: OfferId;
  readonly dungeonId: DungeonId;
  readonly riskLevel: RiskLevel;
  readonly party: ExpeditionParty;
  readonly lockReason: OfferLockReason | null;
  readonly reward: ContractReward;
}
```

위험도별 양끝을 포함한 정수 범위와 기대값은 다음과 같다.

| 위험도 | 명성 범위 | 명성 기대값 | 골드 범위 | 골드 기대값 |
| --- | ---: | ---: | ---: | ---: |
| ★1 | 5~7 | 6 | 10~14 | 12 |
| ★2 | 9~11 | 10 | 16~24 | 20 |
| ★3 | 13~17 | 15 | 27~37 | 32 |
| ★4 | 19~23 | 21 | 40~50 | 45 |
| ★5 | 25~31 | 28 | 54~66 | 60 |

각 범위의 모든 정수는 같은 확률을 갖는다. 명성과 골드는 서로 독립된 두 번의
추첨이다. 따라서 명성은 높지만 골드는 낮은 공고처럼 자원 사이의 비교 선택이 생길
수 있다. 두 값이 모두 높거나 낮을 수도 있고, 서로 다른 입력이 우연히 같은 값을
만드는 것도 정상이다.

각 위험도의 최댓값은 다음 위험도의 최솟값보다 작다. 랜덤 범위가 위험도 위계를
역전시키지 않는다.

## 4. 생성 시점과 결정성

`createBoardOffers`가 던전과 파티를 공고로 묶을 때 잠금 여부와 관계없이 보상을
함께 확정한다. 공고별 기본 RNG 키는 다음 문자열이다.

```text
${campaign.seed}/offer-reward/${campaign.worldTurn}/${dungeon.id}/risk-${dungeon.riskLevel}
```

이 키로 만든 결정적 RNG에서 명성을 먼저, 골드를 다음으로 추첨한다. 보상 키는
파티 편성·게시판 선택·화면 카드 순서 스트림과 분리한다. 따라서 다음이 성립한다.

- 같은 캠페인 시드·월드턴·던전 ID·위험도는 같은 보상을 만든다.
- 렌더링 횟수와 화면 카드 순서는 보상을 바꾸지 않는다.
- 같은 월드턴에 승급해 게시판을 다시 만들어도 같은 던전·위험도 보상은 유지된다.
- 월드턴이나 던전 위험도가 바뀐 다음 게시판은 새 키로 보상을 만든다.

보상은 분포상 충돌할 수 있으므로 “입력이 다르면 값도 반드시 다르다”는 불변식은
두지 않는다.

## 5. 생존 보상과 전멸 손실

확정 보상에 기존 생존 비율을 자원별로 곱하고 각각 소수점을 버린다.

| 생존 인원 | 계약 보상 비율 |
| ---: | ---: |
| 3명 | 100% |
| 2명 | 60% |
| 1명 | 30% |
| 0명 | 계약 보상 없음 |

예를 들어 공고의 확정 보상이 명성 16·골드 35라면 결과는 다음과 같다.

- 3명 생존: 명성 16·골드 35
- 2명 생존: 명성 9·골드 21
- 1명 생존: 명성 4·골드 10
- 전멸: 계약 골드 0, 명성 -16, 기존 유품 회수 적용

전멸 명성 손실은 위험도 표의 평균이나 새 위험도의 보상이 아니라 계약 당시
`ContractReward.reputation`이다. 명성 하한 0, 유품 골드, 위험도 +1과 ★5 상한은
기존 규칙을 유지한다.

## 6. 데이터 흐름과 검증 경계

```text
createBoardOffers
→ BoardOffer.reward
→ ActiveExpeditionContext.offer.reward
→ SettlementSnapshot.contractReward
→ settleExpedition
→ SettlementResult의 실제 증감과 원인 사슬
```

`SettlementSnapshot`에는 다음 필드를 추가한다.

```ts
readonly contractReward: ContractReward;
```

`createSettlementSnapshotFor`는 활성 원정의 `offer.reward`를 복사한다. 캠페인 전이
계층은 외부에서 받은 snapshot의 보상이 활성 공고 보상과 정확히 같은지 검사한다.
독립적으로 호출할 수 있는 정산 규칙도 두 값이 안전한 정수이고 계약 위험도의
허용 범위 안인지 검사한다.

정산은 캠페인의 현재 공고 배열이나 위험도 표에서 보상을 다시 찾지 않는다. 이
경계는 게시판 갱신과 정산 규칙의 수명을 분리하고, 계약 당시 값이 단일 근거가 되게
한다.

기존 `rewardForSurvivors(risk, survivors)`는 위험도 대신 확정 보상을 받는 순수
계산으로 바꾼다. 위험도별 고정 보상표는 범위표와 공고 생성 함수로 대체한다.

## 7. 화면과 백테스트

### 게시판과 계약 상세

- 공고 카드와 상세 패널은 `offer.reward`의 정확한 값만 표시한다.
- 범위와 추첨 확률은 화면에 노출하지 않는다.
- 생존 결과표는 같은 `offer.reward`로 100%·60%·30% 결과와 전멸 손실을 만든다.
- 잠금 공고도 확정 보상을 보여주지만 계약할 수는 없다.

### 정산

- 실제 명성·골드 증감과 원인 사슬은 snapshot의 확정 보상으로 계산한다.
- 전멸 뒤에는 위험도 상승과 기존 손실·유품만 보여준다.
- `SettlementResult.nextReward`, U6 뷰의 `nextReward`, 다음 보상 UI와 전용 CSS를
  제거한다.
- 다음 공고 보상은 월드턴 뒤 게시판을 새로 만들 때 처음 확정하고 공개한다.

### 백테스트

백테스트 공개 상태의 `fullSurvivorReward`는 위험도 재계산이 아니라
`offer.reward`를 그대로 사용한다. 전략은 플레이어에게 공개된 실제 확정값만 보고
공고를 비교한다.

## 8. 오류 처리

- 공고 생성에 없는 위험도 범위를 요청하면 기존 도메인 타입과 생성 검증에서
  거부한다.
- snapshot 보상이 안전한 정수가 아니거나 해당 계약 위험도 범위를 벗어나면
  `INVALID_SETTLEMENT`로 거부한다.
- snapshot 보상이 활성 원정 공고 보상과 다르면 `INVALID_TRANSITION`으로 거부한다.
- 잘못된 입력을 평균값이나 위험도 표로 조용히 대체하지 않는다.
- 같은 입력의 재실행이 다른 공고·snapshot·정산 결과를 만들면 결정성 회귀다.

## 9. 테스트 전략

구현은 다음 회귀를 먼저 실패시키고 최소 변경으로 통과시킨다.

1. 범위표의 양끝과 산술 기대값이 기존 6/12, 10/20, 15/32, 21/45, 28/60과 같다.
2. 같은 시드·월드턴·던전·위험도는 같은 보상을 만든다.
3. 생성된 모든 명성·골드는 해당 위험도 범위 안에 있다.
4. 잠금 공고에도 보상이 있고 같은 월드턴의 승급 재생성에서 유지된다.
5. 보상 생성이 명성 범위와 골드 범위로 RNG 정수 추첨을 각각 한 번씩 호출하고,
   한 공통 백분위에서 두 값을 함께 환산하지 않는다.
6. 3/2/1명 생존은 100%/60%/30%와 자원별 버림을 적용한다.
7. 전멸 손실은 `contractReward.reputation`과 일치한다.
8. snapshot 보상 변조와 범위 밖 보상을 거부한다.
9. 게시판 재렌더링과 계약부터 정산까지 확정 보상이 유지된다.
10. 전멸 정산에 미래 보상 필드와 문구가 없고, 다음 게시판은 상승한 위험도 범위의
    새 보상을 가진다.
11. 공개 상태 전략, 전체 Store 순회, 캠페인 재현성, 통계·이력 소비가 새 계약을
    사용한다.

## 10. 백테스트 절차와 중단 조건

기대값은 유지되지만 개별 계약과 공고 선택이 달라지므로 전체 캠페인 흐름을 다시
측정한다. 구현 전 기준선을 보존하고 같은 calibration 계열에서 조합당 50·100·200
시드를 순서대로 실행한다.

비교 항목은 다음과 같다.

- B/A/S 승급 도달률과 평균 최초 도달 원정
- 현재·누적 골드와 골드 승급 빈도
- 정상 완주·인력 소진·실직·누적 고발·불신 분포
- 생존·기회주의·선별적 배신 전략의 상대 가치
- 실행 오류·거부·진행 한도 초과·비결정성 0건

이번 변경은 보상 범위 보정을 위한 calibration이 아니다. 의미 있는 회귀나 기존
강제 gate 실패가 나오면 범위·비율을 임의로 수정하지 않고 결과와 조정안을 다시
승인받는다. 현재 공식 B1 문서가 전체 캠페인 holdout을 별도 검토 뒤 실행하도록
정했으므로 이번 변경만으로 2,000시드 holdout을 실행하거나 승인하지 않는다.

## 12. 완료 조건

- 모든 `BoardOffer`가 허용 범위 안의 결정적 `reward`를 가진다.
- 명성·골드는 독립 균등 추첨이며 위험도별 기대값과 위계를 유지한다.
- 게시판은 확정값만, 정산은 계약 당시 값만 사용한다.
- 3/2/1명 생존의 100%/60%/30%와 전멸 명성 손실이 정확하다.
- 미래 보상 필드·정산 표시·전용 스타일이 제거된다.
- 다음 게시판은 새 월드턴과 현재 위험도로 보상을 새로 확정한다.
- 단위·전이·화면·Store·재현성 테스트와 lint·typecheck·build가 통과한다.
- 50·100·200시드 calibration 결과와 기존 기준선 차이가 기록되고 실행 오류와
  비결정성이 0건이다.
- 공식 문서, 타입, 규칙, 화면, 백테스트 공개 상태가 같은 계약을 설명한다.
