# UI 구현 가이드

## 목적

Dungeon Schemer의 UI, 파티원 카드, 지도, 던전 장면, 아이콘, 배경과 기타 시각 에셋을 구현할 때 공통으로 지켜야 하는 작업 규칙을 정한다.

이 문서는 개별 화면의 게임 규칙이나 수치를 새로 정의하지 않는다. 화면별 기능과 데이터는 `GAME_PRINCIPLES.md`, `design`, `systems`, 해당 화면 설계 문서를 따른다. 이 문서는 그 공식 규칙을 실제 UI와 이미지로 옮길 때의 구현·검증 기준이다.

## 문서 우선순위

UI나 이미지 작업을 시작하기 전에 다음 순서로 문서를 읽는다.

1. `docs/GAME_PRINCIPLES.md`
2. 작업 대상과 직접 관련된 `docs/design`·`docs/systems` 공식 문서
3. `docs/experience/SCREEN_LAYOUT.md`
4. `docs/experience/ONBOARDING_AND_INTERFACE.md`
5. 이 `UI_IMPLEMENTATION_GUIDE.md`
6. 해당 작업의 `UI_TASK` 문서
7. 승인된 레퍼런스 이미지와 에셋보드

상위 공식 문서와 하위 레퍼런스 이미지가 충돌하면 상위 공식 문서를 따른다. 레퍼런스 이미지에 공식 데이터와 다른 텍스트가 있어도 그 텍스트를 게임 규칙으로 복사하지 않는다.

## 기존 구현 우선 확인

새 UI를 만들기 전에 반드시 현재 저장소를 확인한다.

- 이미 구현된 비슷한 화면
- 재사용 가능한 React 컴포넌트
- 기존 CSS와 반응형 규칙
- `public/assets`의 기존 에셋
- `docs/diagram`과 해당 화면의 승인 레퍼런스
- 화면이 사용하는 공식 domain/rules/state 데이터

비슷한 컴포넌트나 에셋이 이미 있으면 새로 만들기보다 재사용한다.

## 공통 화면 구조

기본 캠페인 화면은 `GameShell`을 사용한다.

```text
GameShell
├─ TopStatusBar
├─ MainContent 60%
└─ RightPanel 40%
```

- 기본 좌우 비율은 3:2, 즉 60:40이다.
- 화면이 바뀌어도 공통 상태바의 위치와 의미를 유지한다.
- 명시적으로 승인된 예외 화면만 별도 구조를 사용한다.
- UI 작업 때문에 domain/rules 데이터를 임의로 재계산하거나 새로 만들지 않는다.

## 자동 전투 장면 구현

자동 전투의 게임 규칙과 결과 계약은 [던전 이벤트와 보스 시스템](../systems/DUNGEON_EVENTS_AND_BOSSES.md)을 따른다. UI는 던전 진행 화면의 장면 슬롯에서 **이미 계산된 전투 결과를 보여주는 표현 계층**만 담당한다.

### 데이터 흐름

```text
일반 몬스터: E3 확정 결과 ─┐
                           ├→ 자동 전투 장면 재생
보스전: E4 턴 기록 ────────┘
```

- 일반 몬스터 장면은 E3가 확정한 사건·전투 결과를 사용한다.
- 보스전은 E4가 남긴 턴별 공격자·대상·피해·HP 결과를 사용한다.
- UI에서 피해량, HP, 신뢰, 수용·의심·적발, RNG를 다시 계산하지 않는다.
- 애니메이션이 끝나야 규칙 결과가 확정되는 구조를 만들지 않는다. 규칙 상태가 먼저 확정되고 화면이 그 결과를 순차적으로 보여준다.
- 애니메이션을 빠르게 재생하거나 건너뛰어도 같은 최종 상태에 도달해야 한다.
- 현재 replay frame의 `hpByParticipantId`를 전투 참가자와 우측 파티 카드가 함께 사용한다. 별도 timer나 보간 상태를 만들어 두 HP 표시가 어긋나게 하지 않는다.
- Store가 이미 최종 상태여도 진행 화면은 현재 피드백 단계의 projection만 표시한다. 전투 뒤 검증되는 신뢰와 전체 결과가 replay보다 먼저 DOM이나 뒤집기 이력에 나타나면 안 된다.

일반 몬스터 전투와 보스전의 재생 상태는 진행 화면의 우측 하단 CTA와 연결한다. 재생 중에는 그 자리에 `전투 건너뛰기`를 두고 다음 단계 이동 콜백을 노출하지 않는다. complete frame에 도달하면 HP 반영과 사후 대화를 거쳐 `반응 확인`을 제공하고, 신뢰 변화 연출까지 끝난 뒤에만 일반전은 같은 자리를 `지도로 돌아간다`, 보스전은 `정산으로`로 바꾼다. 사후 검증이 없으면 complete 뒤 HP 반영만 끝내고 다음 CTA로 간다. 전체 피드백 시퀀스가 끝난 뒤에만 `다시 보기`를 노출한다. 다시 보기는 이미 확정된 전투 frame만 처음으로 되돌리며 확인한 신뢰를 재적용하거나 캠페인 상태를 바꾸지 않는다. 호출부는 일반전과 보스전의 게이트를 명시적으로 지정하고, 적용 여부나 다음 CTA를 replay 존재 여부 또는 버튼 문구로 추측하지 않는다. 비전투 사건의 CTA는 이 게이트를 사용하지 않는다.

### 1차 프로토타입 표현

캐릭터와 몬스터는 **정적 투명 PNG 한 장**을 기본으로 하고 Framer Motion으로 다음 다섯 표현을 조합한다.

1. `Idle`: 대기 중 미세한 상하 움직임
2. `Attack Lunge`: 공격자가 대상 방향으로 짧게 전진한 뒤 복귀
3. `Hit Shake`: 피격자의 짧은 좌우 흔들림
4. `Damage Number`: 확정된 피해·회복 숫자가 떠오른 뒤 사라짐
5. `HP Bar`: 이전 HP에서 확정 결과 HP까지 부드럽게 보간

한 행동은 원칙적으로 `공격자 강조 → Attack Lunge → Hit Shake + Damage Number → HP Bar 반영 → 원위치` 순서로 읽히게 한다. 동시에 여러 효과를 겹쳐 원인과 결과를 알아보기 어렵게 만들지 않는다.

`HP Bar 반영` 단계에서는 전투 장면의 대상 HP와 우측 파티 카드 HP가 같은
frame 값으로 함께 감소한다. HP가 0이 되는 frame에서 카드의 사망 상태도 함께
바뀐다. 전투 뒤 신뢰 변화는 장면 하단 대사 리본과 `반응 확인` 뒤에 별도
단계로 연출하며 전투 HP frame에 섞지 않는다.

이동 거리, 흔들림 범위, 숫자 위치처럼 캔버스 크기에 종속되는 값은 고정 캔버스 규칙에 맞춰 `rem`, `cqw`, `cqh`를 사용한다. 전투용 PNG는 실제 장면 슬롯에서 캐릭터와 몬스터의 실루엣이 분리되도록 충분한 투명 여백과 해상도를 확보한다.

### 1차 범위 밖

- 캐릭터별 다프레임 idle/attack/hit/dead 스프라이트 세트
- Spine, Live2D 같은 별도 골격 애니메이션 시스템
- 직업별 고유 공격 프레임
- 검격·화살·마법 전용 이펙트 세트
- 복잡한 카메라 줌·흔들림·슬로모션

기본 다섯 표현을 실제 플레이 화면에서 검증한 뒤 필요할 때 별도 폴리시 작업으로 확장한다.

### 비전투 파티 장면

전투 replay가 없는 진행 장면에도 현재 파티가 현장에 있음을 보여준다.

- 기존 파티원 PNG를 재사용하고 새 캐릭터 자산을 만들지 않는다.
- 오른쪽을 바라보는 원본 방향을 유지해 장면 좌측 하단에 배치한다.
- 세 인물의 높이와 크기는 안정적인 파티 슬롯 순서에 따라 조금 달리해 깊이감을 주되 정보나 상태 차이를 암시하지 않는다.
- 우측 파티 상태 카드와 역할이 다르므로 이름·HP·신뢰를 장면 위에 중복하지 않는다.
- 전투 replay가 있으면 비전투 파티 장면을 숨겨 전투 참가자와 겹치지 않게 한다.

## 시각 언어

전체 화면은 현대적인 SaaS 대시보드가 아니라 다크 판타지 길드와 던전 세계 안의 물건처럼 보여야 한다.

주요 재질:

- 짙은 목재
- 검고 낡은 금속
- 양피지와 낡은 종이
- 따뜻한 금빛 광원
- 금색 장식과 구분선
- 낮은 채도의 암색 배경 질감

색 의미:

- 초록: 활성, 선택, 진행 가능, 수용
- 금색: 강조, 선택 가능, 중요 정보
- 붉은색: 위험, 잠금, 진입 불가, 실패

색만으로 상태를 전달하지 않고 텍스트, 형태, 테두리 또는 아이콘을 함께 사용한다.

## 기존 디자인 계승

새 화면은 직전 화면과 같은 게임 안에 있다는 느낌을 유지한다.

우선 재사용하는 대상:

- `TopStatusBar`
- 주요 CTA 조형
- 금색 divider
- 골드·명성·등급 등 기존 상태 아이콘
- 패널 프레임
- 양피지
- 목재·암색 텍스처
- 승인된 압정, 장식, 문양

새 화면마다 비슷한 요소를 다른 스타일로 다시 그리지 않는다.

## 이미지 에셋 생성의 필수 절차

사용자가 이미지 에셋, 캐릭터, 던전, 배경, 지도 장면, 몬스터, 보스, 아이템 그림 등을 만들어 달라고 하면 바로 생성하지 않는다. 먼저 저장소의 관련 GitHub MD와 승인된 시각 자료를 읽고 시각 계약을 파악한다.

**이미지 생성은 프롬프트 작성보다 문서·레퍼런스 확인이 먼저다.** 저장소에 관련 MD가 있으면 기억이나 일반적인 다크 판타지 관습으로 대신하지 않는다. 기존 문서가 지정하는 화면 역할과 승인 이미지가 보여 주는 아트 방향을 실제 생성 프롬프트의 기준으로 사용한다.

최소 확인 항목:

1. 대상 화면의 역할과 정보 위계
2. 기존 화면의 아트 스타일
3. 카메라 시점과 카메라 높이
4. 원근감과 투시 방향
5. 피사체가 바라보는 방향
6. 구도와 화면 안 피사체 크기
7. 조명 방향과 명암 대비
8. 재질 표현과 표면 질감
9. 색 온도와 채도
10. 실제 UI에서 들어갈 슬롯의 가로세로 비율과 예상 표시 크기

### 레퍼런스 스타일을 따라야 하는 범위

레퍼런스를 참고한다는 것은 색상만 비슷하게 만드는 것이 아니다. 가능한 한 다음을 함께 맞춘다.

- 그림의 묘사 밀도
- 실루엣의 복잡도
- 선의 유무와 굵기
- 질감의 거칠기
- 명암 단계
- 광원의 위치
- 배경과 피사체의 분리 방식
- 카메라 거리
- 시점: 정면, 측면, 3/4, 사선, 탑다운 등
- 캐릭터나 몬스터의 바라보는 방향
- 원근 왜곡 정도
- 프레임 안 여백

예를 들어 기존 게임 에셋이 어두운 회화풍 3/4 시점이라면, 같은 대상을 새로 만들 때 갑자기 평면 정면 아이콘이나 로고처럼 만들지 않는다.

**시점은 스타일의 일부다.** 같은 색과 재질을 사용해도 기존 레퍼런스가 왼쪽 3/4 시점인데 새 에셋을 정면으로 만들면 같은 스타일로 보지 않는다. 캐릭터·몬스터·던전·맵 모두 기존 레퍼런스의 카메라 방향과 시점을 우선 계승한다.

## 벡터·아이콘화 금지 원칙

사용자가 명시적으로 아이콘, SVG, 로고, 심볼, 픽토그램 또는 벡터 스타일을 요청하지 않는 이상, 이미지 에셋을 임의로 벡터/플랫 아이콘 느낌으로 단순화하지 않는다.

특히 다음 요청은 기본적으로 장면형 또는 그림형 에셋으로 해석한다.

- 던전 이미지
- 파티원 초상
- 몬스터와 보스
- 지도 배경
- 사건 장면
- 길드 내부 배경
- 아이템 일러스트
- 화면 배경

하지 않는 것:

- 기존 회화풍·픽셀풍·질감형 레퍼런스를 플랫 SVG처럼 재해석
- 원근이 있는 장면을 동그란 심볼이나 로고로 축약
- 3/4 시점 캐릭터를 정면 아이콘으로 임의 변경
- 승인된 에셋보드가 있는데 전혀 다른 화풍으로 새로 생성
- 실제 화면 슬롯에 필요한 장면 대신 장식용 문양만 제작

아이콘이 필요한 위치와 장면형 이미지가 필요한 위치를 혼동하지 않는다.

## 에셋보드와 레퍼런스 이미지 사용

사용자가 특정 에셋보드 또는 승인 이미지를 제공했다면 가능한 한 그 자료를 최우선 시각 기준으로 사용한다.

- 그대로 사용할 수 있는 에셋은 추출하여 재사용한다.
- 새로 만들어야 하는 에셋은 보드의 스타일, 시점, 조명, 질감과 구도를 이어서 만든다.
- 에셋보드의 작은 이미지를 큰 화면에서 과도하게 확대하지 않는다.
- 필요하면 목표 슬롯 비율에 맞는 고해상도 개별 에셋을 다시 제작한다.
- 전체 UI 레퍼런스 한 장을 과도하게 확대·crop해 실제 게임 이미지처럼 쓰지 않는다.

## 이미지 슬롯 기준

이미지는 실제 UI에서 보이는 슬롯을 기준으로 만든다.

작업 문서에 다음을 명시한다.

- 슬롯 비율 예: `16:9`, `1:1`, 세로 초상
- 최소 원본 해상도
- `object-fit` 또는 crop 방식
- 작은 화면과 큰 화면에서의 예상 표시 크기

큰 화면에서 흐릿해지지 않도록 표시 최대 크기보다 충분한 원본 해상도를 확보한다.

## 텍스트 가독성

텍스트는 화면 크기에 따라 함께 확대·축소한다.

- 단순 `vw`만 보지 않고 필요하면 `vw + vh` 기반 `clamp()`를 사용한다.
- 큰 화면에서 텍스트가 작은 크기로 고정되지 않게 한다.
- 작은 화면에서 핵심 정보가 잘리거나 카드 밖으로 넘어가지 않게 한다.
- 공간이 부족하면 텍스트보다 장식, 이미지, padding, gap을 먼저 줄인다.
- 의미가 연결된 정보는 가능한 한 같은 행에 둔다.

예:

```text
[골드 아이콘] 소지 골드    24
[명성 아이콘] 명성 10    [골드 아이콘] 골드 20
```

계약 보상처럼 명성과 골드가 하나의 결과를 이루는 정보는 별도 요구가 없다면 한 행을 유지한다.

## 고정 캔버스 규칙

화면은 1920×1080 고정 캔버스 안에서만 그린다. 창 크기에 따라 배치를 바꾸지 않는다. 자세한 규격은 [화면 규격](SCREEN_LAYOUT.md)에 있다.

새 CSS를 쓸 때 지킬 것:

- 페이지는 가능한 한 단일 최상위 DOM 요소를 반환한다. 이 화면 루트는 공통
  캔버스 규칙으로 폭·높이 100%를 자동 상속한다.
- 화면 루트에 `min-h-screen`, `100vh`, 화면별 `height: 100%`를 반복해서 쓰지
  않는다. 브라우저가 아니라 `.game-canvas`가 화면 크기의 기준이다.
- 내부의 의도적인 여백은 허용한다. 전체 점유는 내부 요소를 화면 끝까지
  늘리라는 뜻이 아니다.
- 전체 점유가 아닌 화면은 승인된 spec과 테스트를 먼저 마련하고 최상위 요소에
  `data-canvas-layout="intrinsic"`을 명시한다.
- 크기는 `rem`으로 쓴다. 루트 글꼴 크기가 축척이라 캔버스와 함께 움직인다.
- 캔버스 비율에 기대야 하는 값은 `cqw`·`cqh`를 쓴다. 캔버스가 크기 컨테이너다.
- `vw`·`vh`를 쓰지 않는다. 창을 가리키므로 캔버스와 어긋난다.
- 미디어 쿼리를 추가하지 않는다. 캔버스 크기가 고정이라 항상 참이거나 항상 거짓이 된다.
- `px`는 `1px` 테두리·구분선처럼 배율과 무관하게 선명해야 하는 값에만 쓴다. 무늬 주기와 큰 그림자 번짐은 `rem`으로 쓴다.

검증 viewport는 창 비율만 확인하면 된다.

- 1920×1080, 2560×1440 (16:9 — 레터박스 없음)
- 1440×900 (16:10 — 위아래 띠)
- 1280×1024 (5:4 — 위아래 두꺼운 띠)

검증 항목:

- 60:40 계약 유지
- 가로·세로 스크롤 없음
- 캔버스 비율이 정확히 16:9이고 가운데 정렬됨
- 네 viewport의 줄바꿈과 상대 배치가 서로 동일함
- 카드 안 텍스트와 이미지 overflow 없음
- 이미지 비율 왜곡 없음
- 중요한 수치가 읽을 수 있는 크기 유지

캔버스 안에서 세로 공간이 부족하면 다음 순서로 압축한다. 창 크기가 아니라 콘텐츠 양 때문에 생기는 문제다.

1. 장식 여백
2. 이미지 크기
3. 패널 padding
4. 장식 아이콘
5. 카드 간 gap
6. 마지막으로 핵심 텍스트

## 파티 UI 규칙

파티원 카드의 기본 정보:

- 초상
- 이름
- 직업
- 성격
- HP
- 신뢰
- 소지 골드

실제 데이터는 domain/state에서 가져온다. 이미지가 준비되지 않았다면 선택적 portrait 매핑 또는 승인된 placeholder를 사용한다.

같은 의미의 아이콘과 라벨은 같은 행에 둔다.

```text
[골드 아이콘] 소지 골드    24
```

아이콘이 라벨 위로 튀거나 숫자와 관계없는 위치에 놓이지 않게 한다.

## 지도 UI 규칙

지도는 단순한 관리용 노드 그래프보다 던전 공간처럼 보여야 한다.

구별해야 하는 상태:

- 현재 위치
- 방문 완료
- 선택 가능한 다음 지점
- 선택 불가능한 다른 갈래
- 보스방

색뿐 아니라 형태, 문양, 테두리, 명암으로도 구별한다. 지도 장면을 생성할 때도 기존 문서와 레퍼런스의 시점과 카메라 방향을 먼저 확인한다.

## CTA 규칙

주요 행동 버튼은 화면에서 쉽게 찾을 수 있어야 한다.

- 텍스트와 장식 이미지를 같은 중심선에 정렬
- viewport 밖으로 밀리지 않게 마지막 행 또는 명시적 공간 확보
- 좁은 화면에서는 텍스트보다 장식 이미지를 먼저 축소
- disabled 상태는 색과 문구를 함께 사용
- 큰 화면에서는 버튼과 텍스트가 지나치게 작게 남지 않게 반응형 확대

## 데이터 규칙

UI에서 공식 게임 데이터를 임의 생성하지 않는다.

UI가 하지 않는 일:

- 파티 재생성
- 위험도 재계산
- 보상 재정의
- 임의 위험 태그 생성
- 시스템 문서에 없는 규칙 추가
- 전투 피해·HP·신뢰·RNG 재계산

필요한 데이터가 현재 모델에 없다면 사용자에게 확인하거나 관련 시스템 작업으로 분리한다.

## 접근성

- 클릭 가능한 카드는 실제 `button` 사용
- 선택 상태는 `aria-pressed` 등 의미 있는 상태 제공
- 잠김 상태는 disabled 또는 명시적 상태 제공
- 색만으로 상태를 전달하지 않음
- 키보드 `focus-visible` 제공
