# 세션 저장 검토

뒤로가기가 게임 진행을 되돌리는지, 무엇이 캐시에 남는지, 실제로 저장해야 할
것이 무엇인지 정리한다. 2026-08-26 에 현재 코드 기준으로 다시 확인했다.

`I1`(상태 머신·스토어)을 시작할 때 읽을 문서다.

## 지금 상태

### 캠페인 진행은 시드와 조작 기록으로 이어진다

`/campaign`의 `CampaignState`와 `CampaignTransitionContext`는 Zustand Store의
현재 탭 메모리에 있지만, 그 판을 다시 세울 재료는 `localStorage`에 남는다. 키는
`dungeon-schemer.campaign-run.v1`이고 payload는 `version`, `seed`, `actions`
세 값뿐이다.

**상태를 통째로 적지 않는다.** `C7 transitionCampaign`이 순수 리듀서이고 열한 개
난수 스트림이 전부 시드에서 나오므로, 같은 시드에 성공한 조작을 같은 순서로 넣으면
같은 캠페인이 선다. 되살리기가 규칙 함수를 다시 지나가므로 **규칙이 허락하지 않는
상태로는 복원될 수 없다.** 상태를 통째로 적으면 손상되거나 손댄 저장이 도달 불가능한
캠페인을 만들 수 있고, 그것을 막으려면 `CampaignState` 전체를 검사하는 코드를 따로
들고 가야 한다.

거부된 조작은 기록하지 않는다. 상태를 바꾸지 않았으므로 다시 넣어도 같은 자리에서
또 거부될 뿐이고, 기록이 실제로 일어난 일과 어긋난다.

되살리기가 어느 한 조작에서 막히면 **앞부분만 살리지 않고 전부 버린다.** 규칙이
바뀌어 옛 저장을 못 읽는 것은 어쩔 수 없지만, 플레이어가 겪지 않은 지점으로 조용히
되돌려 놓는 것은 피한다.

파싱 실패, 규칙 거부, 예상하지 못한 replay 예외를 포함해 복원할 수 없는 저장은
`dungeon-schemer.campaign-run.corrupt-backup`에 최신 원문 한 건과 실패 위치를
남긴 뒤 캠페인 진행 키만 제거한다. 백업 쓰기나 삭제가 실패해도 예외를 화면으로
전파하지 않고 현재 탭의 새 캠페인을 유지한다. 업적 프로필과 오디오 설정은 이
자동 복구의 대상이 아니다.

캠페인과 별도로, 엔딩 뒤 최종 결과만 누적하는 브라우저 업적 프로필이 있다.
`localStorage`의 프로필 payload는
`dungeon-schemer.player-progress.v1` 한 키에 저장한다. 손상된 원문을 정상 V1로
교체할 때만 `dungeon-schemer.player-progress.corrupt-backup` 보조 키를 한 번 쓸 수
있으며, 이것은 두 번째 프로필이나 캠페인 저장이 아니다.

오디오 설정도 캠페인과 분리된 V1 브라우저 설정으로 저장한다. 키는
`dungeon-schemer.audio-settings.v1`이고 payload는 `version`, `bgmEnabled`,
`sfxEnabled` 세 값만 가진다. 최초값은 둘 다 OFF이며 업적 기록 초기화와 캠페인
상태에 영향을 주지 않는다.

### 그런데 화면 상태는 뒤로가기로 살아 돌아온다

| 조작 | 결과 |
| --- | --- |
| `U5` 에서 `진행 기록` 탭 전환 → 다른 화면 → 뒤로가기 | 탭이 **`진행 기록` 그대로** |
| `pageshow.persisted` | **`true`** |
| 새로고침 | `행동 / 조언` 으로 초기화 |
| 앞으로가기 | 정상 |

`persisted === true` 는 브라우저가 **bfcache(back/forward cache)에서 문서를
통째로 되살렸다**는 뜻이다. 화면을 다시 그린 것이 아니라 JS 힙을 그대로
복원했으므로 `useState` 값이 전부 남는다.

## 무엇이 어디에 남는가

| 층 | 지금 | 성격 |
| --- | --- | --- |
| bfcache | **남는다** | 메모리에만, 그 탭에서만. 수명은 브라우저가 정한다 |
| React 전투 속도 Provider | 앱 실행 동안 | `×1`·`×2`. route 전환에는 남고 reload에는 `×1`로 초기화 |
| `localStorage` 업적 프로필 | 1개 | V1 엔딩 결과·누적 업적. 캠페인 상태와 분리 |
| `localStorage` 손상 백업 | 조건부 1개 | 손상 원문을 정상 V1로 교체하기 전 한 번 보관 |
| `localStorage` 오디오 설정 | 1개 | BGM·UI 효과음의 V1 ON/OFF. 최초값은 모두 OFF |
| `localStorage` 캠페인 진행 | 1개 | V1 `seed` + 성공한 조작 기록. 상태 자체는 적지 않는다 |
| `localStorage` 캠페인 손상 백업 | 조건부 1개 | 복원 실패 원문·이유·실패 액션 위치. 최신 한 건만 보존 |
| 업적 화면 저장 진단 | 저장하지 않음 | 앱 소유 키를 읽고 복사하며, 명시적 확인 때 캠페인 진행 키만 삭제 |
| `sessionStorage` | 0개 | 쓰지 않는다 |
| 쿠키 | 없음 | 〃 |
| Next.js Router Cache | 사용 | 메인 메뉴의 실제 Next.js 링크로 메타 화면과 캠페인에 진입한다 |

새로고침·탭 닫기 뒤에도 진행 중인 캠페인은 같은 브라우저에서 이어진다. 업적
프로필과 오디오 설정도 남는다. 이어할 판이 없을 때만 `/campaign` 진입이 새 무작위
시드로 새 캠페인을 만든다.

`?seed=...` 진입은 저장을 **무시하되 지우지도 않는다.** 부탁한 판을 그대로 세워야
자동 테스트와 결함 재현이 성립하고, 그 김에 플레이어의 이어하기를 없애서도 안 된다.

엔딩 화면의 `새 캠페인 시작`은 저장을 지우고 나간다. 지우지 않으면 `/campaign`이
끝난 판을 되살려 같은 엔딩 화면으로 돌아온다.

업적 화면의 우상단 달성 수를 다섯 번 연속 누르면 버그 제보용 저장 진단을 연다.
진단은 현재 origin의 `dungeon-schemer.*` 키만 읽어 캠페인 시드·조작 수·최근
조작과 저장 원문을 보여 주며, 다른 origin 저장이나 앱 밖 키는 수집하지 않는다.
전체 복사는 읽은 내용을 그대로 제보할 수 있게 하지만 서버로 자동 전송하지 않는다.

진단의 `캠페인 초기화`는 확인 뒤 `dungeon-schemer.campaign-run.v1`만 삭제하고
`/campaign`으로 새로 이동한다. 업적 프로필, 업적 손상 백업, 오디오 설정은
삭제하지 않는다. 캠페인 키 삭제가 실패하면 같은 판이 다시 복원될 수 있으므로
이동하지 않고 실패를 알린다.

다른 브라우저·기기에는 공유되지 않으며 Supabase·로그인·서버 동기화는 없다. 오디오 설정이 ON이어도 새 문서에서 브라우저가
재생을 허용하기 전에는 BGM을 강제 시작하지 않고 다음 사용자 입력을 기다린다.

오디오 설정의 JSON·구조가 손상되면 둘 다 OFF인 V1으로 복구한다. 현재 코드보다
미래 버전이면 덮어쓰지 않고 사용 불가로 두며, `localStorage` 접근이 거부되면
현재 탭 메모리에서만 설정을 유지한다. 어떤 실패도 업적 프로필이나 캠페인 상태를
삭제하지 않는다.

전투 재생 속도는 저장 대상이 아니다. 루트 React Provider의 메모리에서만 `×1`·`×2`를
공유해 메뉴와 전투 화면을 동기화하고, 오디오 설정 payload·업적 프로필·캠페인
Store·sessionStorage에는 추가하지 않는다.

## I1 이 다룬 함정

bfcache 가 살아 있는 채로 실제 흐름이 붙으면 문제가 된다. 뒤로가기가 **낡은
화면 상태를 되살리는데, 그것이 권위 있는 캠페인 상태와 어긋난다.**

구체적으로: 계약을 맺고 지도로 갔다가 뒤로 가면 게시판이 `계약 전` 모습으로
되살아난다. 같은 공고를 다시 계약할 수 있다.

이 저장소는 시드 재현성을 강하게 다룬다. 백테스트가 그 위에 서 있다. **화면
상태가 규칙 상태보다 오래 사는 것은 단순 버그가 아니라 재현 불가능을 만든다.**
`I1` 의 완료 기준에 이미 「잘못된 전이 거부」가 있으므로, 뒤로가기로 되살아난
화면도 그 거부 대상에 넣는다.

현재 대응은 세 겹이다.

- `pageshow` 에서 `event.persisted` 가 참이면 Provider가 권위 상태로 다시 그린다.
- `phase`와 원정 컨텍스트가 현재 화면을 정한다.
- 되살아난 조작도 순수 상태 머신이 전이 유효성을 확인하고 거부한다.

어느 쪽이든 **화면이 스스로 기억한 것을 믿지 않는다**는 원칙은 같다.

## 스냅샷이 아니라 재생을 고른 이유

아래 두 표는 **상태를 통째로 저장했다면** 들고 가야 했을 목록이다. 지금은 시드와
조작 기록만 적고 `C7`이 이 값들을 다시 만들어 내므로, 저장에는 하나도 들어 있지
않다. 무엇이 재생으로 복원되는지 확인할 때 읽는다.

### `CampaignState` — 뿌리

`lib/domain/campaign.ts`

| 칸 | 왜 필요한가 |
| --- | --- |
| **`seed`** | **가장 중요하다.** 열한 개 스트림(`pool` `board` `party` `map` `ecology` `card` `event` `boss` `trust` `worldturn` `battle`)이 이 값으로 재현된다 |
| `phase` | 어느 단계에서 끊겼는지 |
| `rank` · `reputation` · `gold` · `cumulativeGold` | `cumulativeGold` 는 승급에 쓰지 않고 엔딩 회고 통계 전용이다 |
| `pool` | 캐릭터 30명의 HP·신뢰·상태 |
| `dungeons` | 15개의 위험도와 클리어 여부 |
| `offers` | 게시판 공고 |
| `worldTurn` | 원정 1회가 세계의 시간 1단위다 |
| `ending` | 끝났다면 무엇으로 |

### `ExpeditionState` — 원정 중이라면 함께

`lib/domain/expedition.ts`

| 칸 | 왜 필요한가 |
| --- | --- |
| `dungeonId` | |
| **`riskLevel`** | **계약 시점 값이다.** 던전이 올라도 이 원정은 이 값으로 정산해야 계약 화면에서 본 위험과 어긋나지 않는다 |
| `party` | |
| `activeRuleIds` · `disclosedRuleIds` | 참인 규칙 3개와, 그중 답사 기록으로 공개한 것 |
| `map` · `currentNodeId` · `visitedNodeIds` | 어디까지 갔나 |
| **`infoRecords`** | 수용한 지연형 조언과 개인별 반응. **보스전과 사후 검증의 입력이라 빠지면 보스전이 틀린다** |
| `pendingMerchantEffect` · `bossResult` · `result` | |

여기에 `C8`의 누적 통계(조언·반응, 전환점, 원정 연대기)가 더해진다.
`U6` 엔딩 화면이 소비한다. 이 목록은 미래 캠페인 이어하기 설계의 입력이며 현재
브라우저 업적 프로필에 저장하는 목록이 아니다.

### 저장하지 말아야 할 것

콘솔 탭 선택, 진행 기록 필터, 전투 재생 프레임 같은 화면 상태다.

공교롭게도 **지금 bfcache 가 되살리는 것이 정확히 이것들이다.** 저장 대상이
아니라 오히려 버려야 할 것이다.

## 정하지 않은 것: 스냅샷이냐 재생이냐

규칙이 결정적이고 시드가 있으므로, 이론상 `seed` 와 **플레이어 선택 이력만**
저장해도 전체를 되살릴 수 있다. 백테스트가 이미 그 성질에 기대고 있다.
저장 용량이 훨씬 작고 시드 재현성 검증을 그대로 쓸 수 있다.

문제는 **규칙이 바뀌면 옛 저장이 다른 결과를 낸다**는 것이다. 상태 스냅샷은
그 문제가 없는 대신 무겁고, 타입이 바뀔 때 마이그레이션이 필요하다.

프로토타입 단계에서는 규칙이 계속 바뀌므로 스냅샷이 안전해 보이지만, `I1`
설계에서 결정할 일이다. 여기서는 선택지와 대가만 적어 둔다.
