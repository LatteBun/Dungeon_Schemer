# AI 개발 전 사전 점검표

## 사용 시점

AI는 코드, 설정, 게임 규칙 또는 문서를 변경하기 전에 이 점검표를 확인한다. 이 문서는 사람용 협업 안내인 [팀 개발 워크플로](TEAM_DEVELOPMENT_WORKFLOW.md)를 보완하며, 충돌하면 [문서 안내](../README.md)의 문서 우선순위를 따른다.

## 구현 전 확인

- [ ] `docs/README.md`와 `docs/GAME_PRINCIPLES.md`를 읽고, 작업과 직접 관련된 공식 문서를 확인했다.
- [ ] 현재 브랜치와 `git status --short` 결과를 확인했다.
- [ ] 영향 파일과 기존 변경을 확인했으며, 다른 작업자의 변경을 덮어쓰지 않는다.
- [ ] 요청이 로그인 없이 핵심 게임 루프를 검증하는 MVP 범위 안에 있는지 확인했다.
- [ ] Supabase, 로그인, 비밀 환경 변수, 운영 도메인을 새로 도입하지 않는다.
- [ ] 게임 규칙이 바뀌면 관련 공식 설계 문서도 같은 변경 단위에서 갱신할 범위를 정했다.

## 작업 중 제약

- [ ] 기능 작업은 `feature/<작업명>` 브랜치에서 수행하고 `main`에 직접 push하지 않는다.
- [ ] 기능 실행 확인은 Codespaces에서 먼저 수행한다.
- [ ] Vercel Hobby는 `main` 통합 데모용이다. 기능 브랜치의 공통 검증 수단으로 사용하지 않는다.
- [ ] 게임 규칙을 UI 컴포넌트에만 숨기지 않고, 테스트 가능한 로직으로 분리하는 방향을 따른다.
- [ ] 요청 범위를 벗어나는 리팩터링, 인증, 데이터베이스, 배포 정책 변경을 임의로 추가하지 않는다.
- [ ] 기존 원본 자료인 `docs/any-ideas/`와 `docs/initialization/`은 수정하지 않는다.

## 구현 후 검증

- [ ] 변경한 핵심 흐름을 Codespaces에서 수동으로 확인했다.
- [ ] 프로젝트 초기화가 완료된 뒤 `pnpm lint`를 실행했다.
- [ ] 프로젝트 초기화가 완료된 뒤 `pnpm typecheck`를 실행했다.
- [ ] 프로젝트 초기화가 완료된 뒤 `pnpm build`를 실행했다.
- [ ] 검증 명령이 아직 구성되지 않았다면 통과했다고 주장하지 않고, 미구성 상태를 작업 결과에 명시했다.
- [ ] `main` 병합 뒤에는 Vercel 데모 URL에서 변경 흐름을 확인한다.
- [ ] 게임 규칙이 UI에서 분리된 뒤에는 Vitest 단위 테스트를 추가할지 검토한다.
- [ ] 화면과 핵심 루프가 안정된 뒤에는 Playwright 브라우저 테스트를 추가할지 검토한다.

## 규칙 변경 시 문서 갱신

다음 중 하나가 바뀌면 이 문서와 [팀 개발 워크플로](TEAM_DEVELOPMENT_WORKFLOW.md)를 함께 갱신한다.

- 브랜치, Pull Request, 리뷰, 병합 규칙
- Codespaces 구성과 패키지 매니저
- Vercel 배포 방식, 소유자, 환경 변수, 도메인
- Supabase 또는 로그인 도입으로 인한 MVP 범위 변경
- 공통 검증 명령과 Vitest·Playwright 도입 기준
